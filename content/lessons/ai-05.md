## Why it matters

Few teams train a large model from scratch. They download a base model, fine-tune it on data gathered from several places, add adapters, and wrap it in templates and serving code. Every piece has an origin, a license, and an integrity story, and a deployment is only as trustworthy as the weakest of them. NIST's Generative AI Profile (NIST AI 600-1) names this risk "Value Chain and Component Integration" and defines it as "Non-transparent or untraceable integration of upstream third-party components," including data. OWASP's 2026 list ranks supply chain fourth (LLM04:2026) and data and model poisoning fifth (LLM05:2026).

MITRE ATLAS documents how the chain breaks. In 2023, researchers at Mithril Security edited an open-source language model to state a false fact and uploaded it to Hugging Face, the largest public model hub, to show how easily a poisoned model could spread (AML.CS0019). In 2025, Unit 42 researchers showed that when a hub account is deleted, someone else can register the same name and publish a malicious model under it; applications and cloud model catalogs still referring to the old name could load the replacement (AML.CS0065). Data is exposed too: Carlini and colleagues estimated in 2023 that they could have poisoned 0.01% of two popular web-scale image-text datasets, LAION-400M and COYO-700M, for about $60.

## The core idea

[[model-provenance|Provenance]] is the documented history of an artifact: who made it, from what, by what process, when, and whether it has changed since. For AI it covers two chains. Data provenance records sources, collection dates, consent, licenses, and processing. Model provenance records the base model, the training and fine-tuning data, the procedure, the versions, and the evaluations.

Start with the assumptions. Every deployment silently assumes that:

1. The files you load are the files the publisher released (integrity).
2. The publisher is who you think it is (authenticity).
3. The training data was what the documentation says, and nobody manipulated it.
4. The model behaves as evaluated, with no hidden triggers.
5. The licenses allow your intended use.
6. The documentation is accurate.

An analogy: a food supply chain. A model card is the nutrition label, a cryptographic digest is the tamper-evident seal, and an inventory of components is the lot record that lets you find and recall a bad batch. The analogy also shows the limit: a seal proves the jar was not opened after packing, not that the food was safe when packed. File integrity can be checked with a [[hash-function]] or a [[digital-signature]]. Behavior cannot be checked that way, because a backdoored model passes ordinary tests. Provenance therefore tells you whom you are trusting and lets you verify that nothing changed along the way; it does not prove the source deserved trust.

## How it works

> [!ETHICS] Only test systems you own or have written permission to test.

### The artifacts in the chain

| Artifact | Typical origin | What can go wrong | Evidence to ask for |
| --- | --- | --- | --- |
| Pretraining data | Web crawls, licensed sets | Poisoning, unlicensed or personal data | Source list, collection dates, item digests |
| Base model | Public hub or vendor | Tampered weights, impostor publisher, reused names | Verified publisher, pinned revision, digest or signature |
| Fine-tuning data | Internal records, public sets | Poisoning, private data, license conflicts | Dataset documentation, consent, snapshot digest |
| Adapters | Hubs, in-house | Same risks as models, often less scrutiny | Same as models |
| Tokenizer and chat template | Bundled with the model file | Hidden instructions in the template | Template review, pinned file |
| Weight file format | Publisher's choice | Code that runs when the file loads | A data-only format; see [secure local deployment](lesson:AI-08) |
| Serving code and libraries | Package registries | Dependency compromise | An [[sbom]], pinned dependencies |

The chat-template row is easy to miss. ATLAS records a 2025 demonstration (AML.CS0064) in which researchers modified the chat template packaged inside a widely used model file format, so the template inserted attacker-chosen instructions into the model's context when a trigger appeared, without changing any weights.

### Poisoning and backdoors

[[data-poisoning|Data poisoning]] is changing training data so the trained model behaves as the attacker wants. NIST AI 100-2 E2025 separates poisoning that degrades a model broadly, poisoning aimed at particular inputs, and backdoor poisoning, and adds model poisoning, in which the attacker modifies the model itself, including through the supply chain. A [[model-backdoor]] is hidden behavior tied to a trigger, such as a rare phrase or pixel pattern, that produces the attacker's chosen output while the model behaves normally otherwise. NIST also describes clean-label attacks, in which poisoned examples carry correct labels and look legitimate to a reviewer.

Web-scale data adds two attacks studied by Carlini et al. (2023). In **split-view poisoning**, a dataset is published as a list of web addresses; if a domain on the list expires, an attacker can buy it and serve different content to everyone who downloads the dataset later. In **frontrunning poisoning**, an attacker edits crowd-sourced pages, such as Wikipedia, just before a scheduled snapshot captures them. Split-view poisoning works because nobody recorded what the original content was; frontrunning works because the snapshot time is predictable, so a malicious edit only has to survive briefly.

### Pin, hash, and sign

A name such as `example-org/helpful-7b` is a mutable pointer. Reference artifacts by immutable identifiers and check them on every load:

```python
# Fragile: a mutable name, resolved from a public hub at load time.
model = load_model("example-org/helpful-7b")

# Pinned: an exact revision, a recorded digest, and a refusal to load on mismatch.
model_path = download("example-org/helpful-7b", revision="3f9c2e1")
if sha256_file(model_path) != INVENTORY["helpful-7b"]["sha256"]:
    raise RuntimeError("model file does not match the reviewed artifact")
model = load_model(model_path)
```

The digest comes from your own review, recorded in an inventory that works like a [[software-supply-chain]] bill of materials for AI components:

```yaml
model: helpful-7b
source: hub.example/example-org/helpful-7b
revision: 3f9c2e1 # immutable commit, not "main"
weights: model.safetensors # sha256 recorded at review time
base_model: example-org/base-7b at revision a71b09c
license: custom; attribution required; commercial use allowed with conditions
training_data: base data described only as "web text"; fine-tuning sets listed below
model_card: present; evaluation omits non-English questions
approved_for: internal tutoring pilot only
reviewed_by: alice
```

Where publishers sign artifacts, verify the signature as well, in the spirit of [[artifact-signing]]; a signature ties the file to a key, which is stronger than a digest posted on the same page as the file.

### Documentation and licenses

A [[model-card]], proposed by Mitchell et al. (2019), is a short document that travels with a trained model and reports its intended uses, how it was evaluated, and its performance across relevant conditions and groups. Datasets need similar documentation: sources, collection methods and dates, consent, known gaps, and license. Both are self-reported. They tell you what the producer claims and make omissions visible, which is useful exactly because missing answers are themselves findings.

Licenses add a separate chain. Model weights, code, and training data can each carry different terms. Some models use common open-source licenses; others use custom licenses with attribution requirements or use restrictions. "Open weights" means you can download the weights, not that any use is permitted. Whether a base model's terms bind a fine-tune depends on those terms, so a reviewer records the chain and escalates conflicts. NIST AI 600-1 lists intellectual property and data privacy among its twelve generative AI risks. Treat license review as part of provenance, and get legal advice for real decisions.

## Worked example

**Reviewing licensing and integrity assumptions.** The `cs101.example` team wants to run StudyBuddy on an open-weight model, `helpful-7b`, fine-tuned on two datasets: the course's own question-and-answer archive and a public set called `edu-qa-web`. Alice, the instructor, leads the review.

**Step 1: Inventory every artifact.** Base model, fine-tuned weights, tokenizer and chat template, both datasets, and the serving code with its dependencies.

**Step 2: Record evidence and gaps.**

| Artifact | License | Integrity evidence | Gap found |
| --- | --- | --- | --- |
| Base model | Custom, attribution required | Revision pinned, digest recorded, no signature | Training data described only as "web text" |
| `edu-qa-web` | CC BY-SA 4.0, per its card | Snapshot digest recorded | No collection dates; scraped forum posts may contain personal data |
| Course Q&A archive | Owned by the college | Internal export, digest recorded | Contains student posts; needs privacy review under [[ferpa]] |
| Chat template | Bundled in the model file | Covered by the file digest | Never read by anyone |

**Step 3: Turn assumptions into checks.** Weights unchanged since review: digest check at every load. Correct publisher: verified organization account and pinned revision. Dataset is the reviewed snapshot: item digests and an internal mirror. No backdoor: cannot be proven, so StudyBuddy stays text-only with no tools, and its answers are monitored with the grounding checks from [the misinformation lesson](lesson:AI-03). License allows use: educational use is permitted, and the team will not redistribute the fine-tuned weights. Student data used with permission: student posts are removed from the fine-tuning set until the privacy review finishes.

**Step 4: Decide and document.** Alice approves an internal pilot with conditions: someone reads the chat template, and the unknown base training data is recorded as accepted residual risk. The decision, evidence, and open items go into the inventory, so the next reviewer knows what was assumed and why.

## Defenses

- **Keep an inventory of AI components** with origins, revisions, digests, licenses, and documentation status. _Limit:_ it is only as current as the process that updates it.
- **Pin by immutable revision and digest, and mirror vetted artifacts internally.** This blocks reused names and silent updates. _Limit:_ it freezes known flaws too, so schedule reviews.
- **Verify signatures** where publishers provide them. _Limit:_ a signature proves who signed, not that the content is safe.
- **Prefer data-only weight formats** over formats that can run code when loaded. _Limit:_ a safe format does not make the weights trustworthy.
- **Require model cards and dataset documentation**, and treat missing answers as findings. _Limit:_ documentation is self-reported.
- **Protect training data**: snapshot and hash it, restrict who can write to it, and record each source. _Limit:_ web-scale data cannot be fully reviewed by people.
- **Contain what you cannot verify**: limit the model's tools and permissions, evaluate on held-out data, and monitor outputs. _Limit:_ monitoring finds problems after deployment.

## Common misconceptions

- **"Popular on the hub means safe."** Download counts and likes are not reviews.
- **"A matching hash proves the model is good."** It proves the file is unchanged, nothing more.
- **"Open weights means open source and free for any use."** Licenses vary and may restrict use.
- **"Testing will reveal any backdoor."** Only tests that contain the trigger reveal it.
- **"Poisoning requires controlling much of the data."** Carlini et al. showed that tiny fractions of web-scale data were within cheap reach.
- **"Model cards are audits."** They are the producer's own account.

## Key takeaways

- An AI system inherits the risks of every artifact behind it: data, base models, adapters, templates, file formats, and code.
- Write down the integrity, authenticity, behavior, and licensing assumptions, and turn each into a check or a documented residual risk.
- Pin by immutable revision and digest; a name on a hub is a mutable pointer.
- Hashes and signatures prove a file is unchanged and who released it, not that its behavior is safe; backdoors evade ordinary tests.
- Model cards and dataset documentation make claims and omissions visible; licenses form their own chain to review.
