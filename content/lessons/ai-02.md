## Why it matters

Organizations increasingly connect language-model assistants to their own documents: wikis, shared drives, tickets, chat channels, and email. The standard technique is [[retrieval-augmented-generation]] (RAG), a name Lewis and colleagues gave the approach in 2020: before the model answers, a search step finds relevant passages and places them in the model's context, so answers can draw on documents the model never saw in training. The technique is useful, and it moves the access-control problem. The assistant becomes a search engine over everything it indexed, with a friendly interface that summarizes whatever it finds.

OWASP's 2026 list ranks sensitive information disclosure second (LLM02:2026) and names oversharing upstream as a structural cause: broad permissions and knowledge bases feed sensitive data into retrieval, and the fix lies in the data surface, not the model. It also states the core technical fact bluntly: "Cosine similarity does not respect ACLs." Similarity search finds the most relevant text, not the text you are allowed to read.

The failure is not hypothetical. In August 2024, the security firm PromptArmor showed that Slack AI could leak data from private channels, a case MITRE ATLAS records as AML.CS0035. An attacker posted crafted instructions in a public channel. When a victim later asked Slack AI a question, the assistant retrieved both the attacker's post and an API key the victim had stored in a private channel, and the injected instructions steered it to place the secret in a link. The attacker never had access to the private channel. The victim's assistant did.

## The core idea

Start with the assumptions. Documents in an organization have owners and access rules, usually an access-control list (ACL) that says which users and groups may read each one. The systems that hold the documents, such as the wiki or the drive, enforce those rules. A RAG pipeline copies the content into a new place, a search index, and serves it through a new interface, the assistant. So ask two questions: does the copy carry the rules with it, and does the new interface enforce them for the person asking?

An analogy helps. A library patron asks a reference librarian for information. The librarian holds keys to the rare-books room. A careful librarian checks the patron's card before fetching anything; a careless one reads the restricted book aloud to whoever asks. An assistant that searches with its own broad permissions is the careless librarian, a classic [[confused-deputy]]: a program with more authority than its caller, tricked or simply allowed into using that authority on the caller's behalf. MITRE ATLAS makes the same point about AI services: agents may reach data that a regular user could not access directly (AML.T0085).

The rule follows: **the assistant must never retrieve anything the asking user could not open directly.** Enforce it in the retrieval query, using the user's identity, not in the prompt and not after generation. A prompt instruction is just more text (see [the prompt injection lesson](lesson:AI-01)). Filtering the answer is too late: once a chunk is in the [[context-window|context window]], the model can quote, paraphrase, or translate it, and OWASP notes that filtering after generation cannot take back a chunk the model has already received.

## How it works

> [!ETHICS] Only test systems you own or have written permission to test.

### The pipeline and where permissions get lost

A RAG system turns documents into searchable numbers. Each passage becomes an [[embedding]], a list of numbers that places text with similar meaning close together, and a [[vector-database|vector database]] stores those vectors with metadata and finds the nearest ones to a question.

| Stage    | What happens                                        | How access control can fail                                          |
| -------- | --------------------------------------------------- | -------------------------------------------------------------------- |
| Ingest   | Connectors read documents from source systems       | A [[service-account]] that can read everything; ACLs not copied     |
| Chunk    | Documents are split into passages                   | Chunks keep the text but lose the document's ACL                     |
| Embed    | Each chunk becomes a vector                         | Vectors exported or backed up without protection                     |
| Index    | Vectors and metadata are stored                     | One flat index shared across teams or customers                      |
| Query    | The question is embedded and nearest chunks found   | The search carries no user identity                                  |
| Generate | Top chunks go into the model's context              | A restricted chunk is now in the context                             |
| Output   | Answer, citations, caches, logs                     | Restricted text or titles leak through side channels                 |

The diagram below shows the most common failure: a search that carries no user identity.

```sequence
title: A shared index leaks a restricted document
participant B as Bob
participant A as Assistant
participant V as Vector index
participant L as LLM
B -> A: What is the salary band for senior engineers?
A -> V: Nearest chunks, no user filter
V --> A: Chunk from hr/compensation-2026.xlsx
A -> L: Question + restricted chunk
L --> A: Summary of the HR-only salary bands
A --> B: Answer reveals HR-only content
note: Bob cannot open hr/compensation-2026.xlsx directly
```

Bob did nothing clever. He asked an ordinary question, and the assistant, searching with its own authority, fetched a file he has never been allowed to open.

### Three places to enforce permissions

1. **In the prompt** ("only use documents the user may see"). This is not enforcement; the model receives the restricted text anyway.
2. **After retrieval.** Search everything, then drop chunks the user may not read before generation. This keeps restricted text out of the context, but restricted documents are still scored and ranked. OWASP's RAG cheat sheet prefers filtering before retrieval because it "prevents the similarity scores of restricted documents from being observed."
3. **Inside the query.** The search considers only chunks whose metadata matches the user's tenant and groups, and returns nothing when metadata is missing (fail closed). For high-sensitivity data, separate indexes per customer or classification level add a second wall. This connects to [[multi-tenancy]] in cloud systems: a flat index shared by customers is a shared database without row-level security.

Here is the vulnerable pattern next to the fix:

```python
# Vulnerable: one shared index, searched with the service's own authority.
def answer(user, question):
    chunks = index.search(embed(question), top_k=5)
    return llm.chat(build_messages(question, chunks))
```

```python
# Fixed: the user's identity is part of the search, and every check fails closed.
def answer(user, question):
    groups = directory.groups_for(user)  # looked up now, not copied at ingest time
    chunks = index.search(
        embed(question),
        top_k=5,
        filter={"tenant": user.tenant, "allowed_groups": {"any_of": groups}},
    )
    chunks = [c for c in chunks if source_acl_allows(user, c.doc_id)]  # live recheck
    return llm.chat(build_messages(question, chunks))
```

The live recheck handles stale permissions: if Bob left the HR group this morning, a nightly copy of the ACL is wrong until tonight, but the source system knows now.

### Leaks that bypass the answer

- **Citations.** A citation list that shows the titles of restricted documents leaks their existence, and titles such as "Q3 layoffs draft" say a lot.
- **Caches.** A cache keyed only by question text can serve one user's answer, built from that user's documents, to someone else.
- **Logs and traces.** OWASP's 2026 list warns that observability tools often record full prompts, completions, and traces by default.
- **Embeddings.** Inversion can rebuild much of the text from vectors, so OWASP treats an exported embedding as sensitive as its source. Its 2026 entry on vector and embedding weaknesses (LLM09:2026) sums up the family: "poisoning makes the system wrong, inversion makes it leak."
- **Injected content.** As the Slack AI case shows, retrieval that respects the victim's permissions can still mix an attacker's instructions with the victim's private data in one context.

## Worked example

**Testing access-scoped search with synthetic identities.** Ledger is a fictional internal assistant at `bank.example` that indexes the wiki, the shared drive, and the ticket system. Before launch, the security team tests whether it respects permissions. They work in a staging copy and never use real employees' accounts or documents.

**Step 1: Create synthetic identities** with known group memberships: `t-alice` (Finance), `t-bob` (Engineering), `t-mallory` (Contractors), and `t-nobody` (no groups).

**Step 2: Plant canary documents.** Each contains a unique random marker and is restricted to one group in its source system:

| Canary marker  | Location                     | Readable by  |
| -------------- | ---------------------------- | ------------ |
| `CANARY-FIN-7Q2` | finance/budget-test.docx     | Finance      |
| `CANARY-ENG-K9D` | eng/design-test.md           | Engineering  |
| `CANARY-HR-3XW`  | hr/test-compensation.xlsx    | HR (no test user) |
| `CANARY-PUB-55B` | wiki/all-groups-test.md      | Every group  |

**Step 3: Write the expected matrix.** `t-alice` may see FIN and PUB; `t-bob` may see ENG and PUB; `t-mallory` may see only PUB; `t-nobody` may see nothing. Every other combination must return nothing.

**Step 4: Probe two layers.** First, call the retrieval API directly as each identity with questions aimed at each canary's topic, and record which chunks come back. This is the strong test, because a model may see a canary and not repeat it. Second, ask the same questions through the chat interface and search answers, citations, cache entries, and logs for any marker.

**Step 5: Test change.** Remove `t-bob` from Engineering, wait the documented propagation time (zero, if the query rechecks live ACLs), and rerun. The ENG canary must disappear.

**Step 6: Read the results.** Suppose retrieval returns `CANARY-FIN-7Q2` to `t-mallory` for the question "summarize recent budget discussions." Tracing the chunk shows it came from a ticket attachment: the ticket connector indexed attachments without their ACLs, and the index treated a missing ACL as "everyone." Two fixes follow. The connector must copy attachment permissions, and the query filter must treat missing metadata as "no one." After the fix, the team reruns the whole matrix, because a fix in one connector says nothing about the others.

## Defenses

- **Filter inside the query, with the end user's identity.** Pass tenant and group membership into the search, recheck the live ACL for returned documents, and fail closed. _Limit:_ only as good as the metadata; a connector that drops ACLs defeats it.
- **Carry permissions to every chunk.** The RAG cheat sheet asks for access metadata on each chunk, not only the source document, and for re-evaluation when source permissions change. _Limit:_ sync lag; keep the live recheck.
- **Partition sensitive data.** Use separate indexes or namespaces per tenant or classification level. _Limit:_ more systems to operate, and partitions do not fix bad ACLs inside one partition.
- **Index less.** Apply [[data-minimization]]: leave out sources the assistant does not need, such as HR or legal files. _Limit:_ users may push for "index everything" once the assistant proves useful.
- **Use least-privilege connectors.** Give each connector's service account read access only to in-scope sources, applying [[least-privilege]]. _Limit:_ the assistant still holds more than any single user.
- **Protect derived data.** Classify embeddings, caches, and logs like their sources, scrub logs, and restrict index exports. _Limit:_ easy to forget as new tools are added.
- **Log and monitor retrieval.** The RAG cheat sheet recommends logging every retrieval with the user's identity and the access metadata of the returned chunks, then alerting on unusual patterns. _Limit:_ logs must themselves be protected.
- **Test continuously.** Run the synthetic-identity matrix in the deployment pipeline and after every connector change. _Limit:_ tests cover only the identities and canaries you planted.

## Common misconceptions

- **"The model will keep confidential documents confidential if we tell it to."** Instructions are not access control. Decide what the model receives, not what it is asked to say.
- **"Filtering the final answer is enough."** Paraphrases, summaries, and translations slip past keyword filters, and citations, caches, and logs bypass the answer entirely.
- **"Embeddings are just numbers, so they are anonymized."** Inversion can recover much of the text. Treat vectors like the documents they came from.
- **"The assistant inherits the source system's permissions."** Only if the pipeline copies them and the query enforces them. Many connectors read everything with one service account.
- **"Testing with my account shows it works."** Administrators can see everything, so their results prove nothing. Test with synthetic low-privilege identities.

## Key takeaways

- Retrieval moves access control: an assistant that searches with its own broad authority becomes a confused deputy for whoever asks.
- Enforce permissions inside the retrieval query, with the end user's identity and a live check, and fail closed when metadata is missing.
- Prompt instructions and answer filters are not access control; once a chunk reaches the context, it can leak.
- Citations, caches, logs, and embeddings are leakage channels too, and deserve the classification of their sources.
- Test with synthetic identities and canaries at the retrieval layer, including permission changes, and rerun after every connector change.

## Go deeper

- Lewis et al. (2020) proposed RAG partly to address two open problems, giving outputs provenance and updating a model's knowledge. Connecting retrieval to private documents created the permission problem this lesson covers.
- OWASP's 2026 entries on sensitive information disclosure (LLM02:2026) and vector and embedding weaknesses (LLM09:2026) catalog leakage channels, from shared caches across tenants to embedding inversion, with tiered mitigations.
- The OWASP RAG Security Cheat Sheet recommends cross-tenant retrieval tests in the deployment pipeline with a target of zero cross-boundary results. An open question for research and practice: how can filtered nearest-neighbor search keep both strong isolation and good recall at scale?
- MITRE ATLAS documents real cases, including the Slack AI exfiltration (AML.CS0035), and catalogs the use of AI services to reach data users could not access directly (AML.T0085).
