## Why it matters

Machine learning models make security decisions: whether a file is malware, a web page is phishing, or a review is spam. Ordinary users do not try to fool them, but an attacker who profits from a wrong decision will search for inputs that produce one. An [[adversarial-example]] is such an input: one deliberately modified, often only slightly, so that a model produces the output the attacker wants.

This happens outside the laboratory. MITRE ATLAS, a knowledge base of attacks on AI systems, records that in 2019 researchers at Skylight Cyber created a universal bypass string that made Cylance's AI malware detector miss malicious files when the string was appended to them (AML.CS0003). ATLAS also records a case reported by Norton Research Group in which attackers had apparently modified brand logos on phishing pages by hand. The changes fooled the classifier that checked for visual similarity to real brands, but the detection system's other classifiers still flagged the pages (AML.CS0032).

NIST AI 100-2 E2025, NIST's taxonomy of adversarial machine learning, calls this an [[evasion-attack]] and warns that current mitigations "tend to be empirical and limited in nature." Szegedy and colleagues reported at ICLR 2014 that state-of-the-art neural networks are vulnerable to adversarial examples; NIST still describes designing models that resist evasion as an open problem.

## The core idea

A classifier maps an input, described by numeric features, to a label. Geometrically, it divides the feature space into regions separated by a decision boundary, and an input near the boundary can be pushed across it by a small change. The attacker looks for a perturbation: a change that is small by some measure, keeps the input useful to the attacker, and crosses the boundary.

Every claim about adversarial examples rests on a [[threat-model]] with three parts:

| Part | Question | Example |
| --- | --- | --- |
| Goal | Any wrong label (untargeted) or a specific one (targeted)? | "Classify my malware as benign" is targeted |
| Knowledge | What does the attacker know about the model? | White-box: its parameters; black-box: only its outputs |
| Capability | Which features can change, and by how much? | Each pixel by at most 2/255; only the text a reviewer writes |

NIST AI 100-2 E2025 describes white-box attackers as knowing the model's architecture and parameters, and black-box attackers as having no prior knowledge of the architecture or training data; gray-box settings lie in between. The capability is often written as a budget ε under a norm: L∞ limits how much any single feature changes, L2 limits the overall Euclidean size of the change, and L0 limits how many features change.

The perturbed input must also work in the problem space, the real-world object behind the features: malware must still run, and a phishing page must still fool people. ATLAS notes that changes are typically "constrained in magnitude or location so that a human still perceives the data as if it were unmodified," though that matters less when no human looks.

[[adversarial-robustness|Robustness]] is defined relative to the threat model: a model is robust at an input if no allowed perturbation changes its decision. A robustness claim without a stated threat model cannot be checked.

Keep evasion separate from [[data-poisoning]] (see [provenance](lesson:AI-05)). Poisoning corrupts the training data or the model so that it learns the wrong thing. Evasion leaves the model untouched and attacks it at deployment time, one input at a time.

## How it works

> [!ETHICS] Only test systems you own or have written permission to test.

### Why small changes add up

Goodfellow, Shlens, and Szegedy (ICLR 2015) argued that the primary cause of the vulnerability is not nonlinearity or overfitting, as earlier explanations suggested, but the models' linear nature. Take a linear score `z = w · x + b`, where `w` holds one weight per feature. Changing `x` by a perturbation `η` changes the score by `w · η`. If each feature may move by at most ε, the largest change comes from moving every feature by ε in the direction of its weight's sign, `η = ε · sign(w)`, which shifts the score by ε times the sum of the absolute weights. With `n` features of average weight magnitude `m`, that is `ε · m · n`: it grows with the number of features while ε stays fixed.

Random changes of the same size behave very differently, because their contributions partly cancel; their typical size grows only with the square root of `n`. Illustrative numbers for ε = 0.01 and m = 0.05:

| Input | Features n | Worst-case change ε·m·n | Typical random change ε·m·√n |
| --- | --- | --- | --- |
| A 4-feature record | 4 | 0.002 | 0.001 |
| 28 × 28 grayscale image | 784 | 0.39 | 0.014 |
| 224 × 224 color image | 150,528 | 75 | 0.19 |

A change of a few units can reverse a confident decision (a logistic model is 99% confident at `z = 4.6` and 99% confident of the opposite at `z = −4.6`), so in high dimensions an imperceptible per-feature change can be decisive. A figure in Goodfellow et al.'s paper shows an image classified as a panda with 57.7% confidence that became a "gibbon" at 99.3% confidence after a perturbation of ε = 0.007, the size of the smallest step in an 8-bit image encoding as that network scaled its inputs. The argument extends to neural networks because many popular components, such as rectified linear units, are piecewise linear.

### Gradient-based attacks

A neural network is not linear overall, but its gradient, the vector of partial derivatives of the loss with respect to each input feature, shows which direction increases the loss fastest near the current input. Goodfellow et al. used it to define the fast gradient sign method (FGSM):

```text
x_adv = x + ε · sign(∇x J(θ, x, y))
```

Here `J` is the training loss, `θ` the model's parameters, and `y` the correct label. One gradient computation moves every feature by ε in the direction that, to a first approximation, hurts the model most. On the MNIST handwritten-digit dataset with ε = 0.25, they reported that this single step gave a shallow softmax classifier a 99.9% error rate and made a maxout network (a type of neural network) misclassify 89.4% of examples, with an average confidence of 97.6% in the wrong answers. Iterative variants take several smaller steps and project the input back into the allowed set after each one, which matters when the model is far from linear over the range of ε.

### Knowledge and access

White-box attackers compute gradients directly; ATLAS calls this White-Box Optimization (AML.T0043.000). Black-box attackers have other routes:

- **Query-based search** (Black-Box Optimization, AML.T0043.001): submit inputs, observe the outputs, and adjust. ATLAS notes that they need more queries than white-box attacks but much less access, and may run through an API the victim monitors.
- **Transfer** (Black-Box Transfer, AML.T0043.002): craft examples on substitute models the attacker controls and use them against the target. Goodfellow et al. highlighted that adversarial examples generalize across architectures and training sets.
- **Manual modification** (AML.T0043.003): trial-and-error edits guided by guesses about what the model relies on, as with the phishing logos above.

The diagram shows a query-based search against a fictional review filter that returns its spam score with every rejection.


Returning the exact score turns the API into a guide for the search. ATLAS recommends returning only what the application needs, such as a label without its confidence score (AML.M0002).

## Worked example

**Analyzing a small transparent model.** The trust-and-safety team at `shop.example`, Alice and Bob, uses ReviewGuard, a logistic-regression spam filter for product reviews. Because the model is linear with four features, its robustness can be computed exactly.

| Feature (scaled 0 to 1) | Weight | Who controls it |
| --- | --- | --- |
| Link density | +2.0 | The review's author |
| Share of capital letters | +1.5 | The review's author |
| Exclamation marks | +1.0 | The review's author |
| Account age | −2.5 | Nobody, in the short term (an assumption) |

The bias is b = −1.0. ReviewGuard computes `z = w · x + b` and flags a review when `z > 0`, which is the same as a spam probability `1 / (1 + e^(−z))` above 0.5.

**Step 1: Score a flagged review.** For x = (0.6, 0.5, 0.4, 0.2), z = 1.2 + 0.75 + 0.4 − 0.5 − 1.0 = 0.85, a spam probability of about 0.70.

**Step 2: Find the worst case under threat model A, where every feature can move by up to ε.** The gradient of `z` with respect to `x` is simply `w`, so the worst case lowers `z` by ε × (2.0 + 1.5 + 1.0 + 2.5) = 7ε. The smallest budget that flips the decision is 0.85 / 7 ≈ 0.12. At ε = 0.15, z falls to −0.20 and the review passes.

**Step 3: Repeat under threat model B, where account age is fixed.** Only 4.5ε is now available. The smallest flipping budget is 0.85 / 4.5 ≈ 0.19, and at ε = 0.15 the score is still 0.175, so the review stays flagged. Same model, same input, different answer: robustness belongs to a model and a threat model together.

**Step 4: Check the budget against the problem space.** Is a budget of 0.19 large? Not here. The three text features are entirely under the author's control and cost almost nothing to change. The real finding is a design flaw: the model relies mostly on signals the attacker controls.

**Step 5: Script the analysis** so it can be rerun after every retraining:

```python
import math

w = [2.0, 1.5, 1.0, -2.5]  # link density, capitals, exclamations, account age
b = -1.0

def score(x):
    z = sum(wi * xi for wi, xi in zip(w, x)) + b
    return z, 1 / (1 + math.exp(-z))  # logit and spam probability

def worst_case_input(x, eps, movable):
    # Move each movable feature by eps against the sign of its weight,
    # staying inside the valid range [0, 1].
    return [min(1.0, max(0.0, xi - eps * math.copysign(1, wi))) if m else xi
            for xi, wi, m in zip(x, w, movable)]

def flip_budget(x, movable):
    z, _ = score(x)
    return z / sum(abs(wi) for wi, m in zip(w, movable) if m)  # ignores [0, 1] limits

review = [0.6, 0.5, 0.4, 0.2]
model_a = [True, True, True, True]   # threat model A
model_b = [True, True, True, False]  # threat model B: account age fixed
print(score(review))                                   # z = 0.85, p = 0.70
print(score(worst_case_input(review, 0.15, model_a)))  # z = -0.20: passes
print(score(worst_case_input(review, 0.15, model_b)))  # z = 0.175: still flagged
print(flip_budget(review, model_a), flip_budget(review, model_b))  # 0.12, 0.19
```

**Step 6: Recommend.** The team records five actions: weight signals that are expensive to fake, such as account history and verified purchases, and check the effect on legitimate new users; stop returning scores; rate-limit submissions per account and watch for many near-identical resubmissions; send borderline scores to human review; and after every retraining, report robust accuracy under both threat models next to clean accuracy.

## Defenses

No single defense solves evasion. NIST AI 100-2 E2025 notes that evasion mitigations involve "inherent trade-offs between robustness and accuracy." Combine several:

- **State the threat model first.** Write down the goal, knowledge, and budget you defend against, and report robust accuracy, the share of test inputs still classified correctly under the worst allowed perturbation, for each. _Limit:_ attackers can step outside your model, as the hand-edited logos did.
- **[[adversarial-training|Adversarial training]].** NIST describes it as a method that "augments training data with adversarial examples generated iteratively during training using their correct labels." Goodfellow et al. reported that it cut a maxout network's error on fast-gradient-sign examples from 89.4% to 17.9% on MNIST. ATLAS groups it with other model-hardening methods (AML.M0003). _Limit:_ protection is strongest against the attacks used in training, and NIST notes it "usually comes at the cost of decreased model accuracy on clean data."
- **Certify robustness.** Certification proves, for a given input, that no perturbation within a stated budget changes the prediction. NIST describes randomized smoothing as transforming "any classifier into a certifiable robust smooth classifier"; [[formal-verification]] is the other main family. _Limit:_ certificates typically cover small budgets under one norm, smoothing's guarantees are probabilistic, and NIST notes verification methods are "limited by their lack of scalability, computational cost."
- **Give attackers less feedback.** Return labels instead of scores (AML.M0002), apply [[rate-limiting]] and quotas per identity (AML.M0004), and monitor for probing patterns (AML.M0015). _Limit:_ transfer attacks and offline copies need few or no queries.
- **Design features and inputs defensively.** Prefer signals attackers cannot cheaply change, and normalize inputs, for example through [[canonicalization]] of look-alike characters in text. _Limit:_ hard-to-fake signals can raise the [[false-positive]] rate for legitimate users, and ATLAS advises evaluating input preprocessing "against adaptive adversaries that account for the preprocessing operation" (AML.M0010).
- **Layer decisions.** Use diverse ensembles (AML.M0006), non-ML checks such as link reputation, and human review for borderline or high-impact cases, following [[defense-in-depth]]. In the phishing case, other components caught what one classifier missed. _Limit:_ components can share blind spots.
- **Evaluate adaptively.** Attack each defense with full knowledge of how it works, and treat robust accuracy measured by attacks as an upper bound, since a stronger attack can only lower it. _Limit:_ only certification gives a lower bound.

## Common misconceptions

- **"Adversarial examples are just noise."** They are optimized. Random changes of the same size mostly cancel, as the table in "How it works" shows.
- **"Our model is 99% accurate, so it is robust."** Accuracy measures typical inputs; an attacker chooses the worst ones.
- **"Keeping the model secret prevents attacks."** Transfer, query-based search, and manual edits all work without the weights.
- **"This is only an image problem."** ATLAS lists evasion of AI-based malware detection and network scanning, and text classifiers such as ReviewGuard are exposed too.
- **"Our defense stopped the attack we tried, so the model is robust."** A defense must survive attackers who know about it.
- **"A model has one robustness number."** Robustness depends on the threat model and budget, as threat models A and B showed.

## Try it yourself

Analyze a second transparent model on paper, in a spreadsheet, or with the Python code above on your own computer. ReviewGuard v2 uses the same four features with weights (1.2, 0.8, 0.5, −3.0) and bias b = 0.0.

1. Score the review x = (0.6, 0.5, 0.4, 0.2) with v2. Is it flagged?
2. Compute v2's smallest flipping budget under threat model A and under threat model B, and compare them with v1's (about 0.12 and 0.19). Under which assumption does v2 gain robustness?
3. A legitimate review from a three-day-old account has x = (0.1, 0.1, 0.2, 0.0). Score it with v1 and with v2. What did v2 give up for its robustness?
4. For v1 with ε = 0.15, choose each feature's direction (up or down) by a coin flip, five times, and compute the change in z each time. Compare your results with the worst case of −1.05 and explain the difference using the table in "How it works".
5. Write a two-sentence robustness claim for v2 that states the goal, the attacker's knowledge, the budget, and one attack the claim does not cover.

_Check yourself:_ v2 scores the review at z = 0.72; its flipping budgets are about 0.13 (A) and 0.29 (B); and it flags the new account's review (z = 0.30), which v1 passes (z = −0.45).

## Key takeaways

- An adversarial example is an input deliberately changed, often slightly, so a model produces the attacker's chosen output. Evasion happens at deployment time; poisoning happens during training.
- In a roughly linear model, the worst-case score change is ε times the sum of the absolute weights, so tiny per-feature changes add up in high dimensions while random changes mostly cancel.
- Robustness is meaningful only relative to a threat model: the goal, the attacker's knowledge, and a budget over the features the attacker can actually change.
- Hiding the model is not enough, because transfer, query-based search, and manual edits work without the weights.
- Adversarial training, certification, limited feedback, robust features, and layered decisions each have limits; evaluate with adaptive attacks and report robust accuracy with its budget.
